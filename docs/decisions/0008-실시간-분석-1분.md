# 0008. 응답 속도: 실시간 분석을 1분 안에 (2026-10-25)

상태: **제안** (사람 확인 필요. 목표 "1분 ±20초", "도시별로 미리 다 돌려 두지 않고 실시간으로 가되 문제를 고친다"는 2026-10-25 팀 결정)

근거: [실험 기록](../../experiments/results/2026-10-21-gemini-observe.md)의 10/25 측정(오사카 영상 5개, 속도 실험 T1~T8·F1~F3·L1).

## 문제

1. **너무 느리다.** 지금은 영상 5개를 하나씩 Gemini로 분석해 약 12분 걸린다. 이 서비스를 쓰는 사람은 영상 보기도 귀찮은 사람이라 몇 분씩 기다리지 않는다. **목표: 요청 → 지도에 핀이 다 찍힐 때까지 60초 ±20초.** 중간 결과를 먼저 보여 줄 필요는 없다(팀 결정).
2. **미리 다 돌려 두는 방식은 못 쓴다.** 도시마다 영상을 미리 분석해 두려면 도시 수 × 영상 수만큼 Gemini를 불러야 하는데, 무료 하루 한도(모델당 20회 안팎)로는 도시 한두 곳도 겨우 채운다.
3. **엉뚱한 영상이 섞인다.** 실제 선택 규칙으로 고른 5개 중 2개가 오사카와 무관(국내 다이어트 브이로그)하거나 방문이 아닌 정보 영상이었다.
4. **503·한도 오류에 약하다.** 하나라도 503이 나면 그 영상은 실패하고, 재시도하면 1분을 넘긴다.

### 2-1. 동시 5개 실측과 화면 흐름 (2026-10-25)

동시 5개(3-flash-preview 2, 3.5-flash-lite 2, 3.8-flash 1): **2번째 완료 23초, 4번째 33초, 마지막 59초**, 503 없음. 자세한 표는 실험 기록.

화면은 장소 단위로, 여러 개를 한 번에 보여 고르게 한다(2026-10-25 팀 결정):

| 시점 | 화면 |
| --- | --- |
| 0~3초 | 고른 영상 5개 카드 |
| 3초~ | Gemini가 찾은 장소 이름을 칩으로 쌓아 보여 줌 ("확인 중", 누를 수 없음). 관찰 단계가 스트리밍으로 받은 단서 일부를 몇 초마다 기록 |

### 3. 분석 결과는 지우지 않고 계속 재사용 (자연스럽게 쌓이는 캐시)

- 도시별로 미리 돌리지 않는다. 대신 **한 번 분석한 영상은 버전이 같으면 계속 재사용**한다(이미 구현, [2-1] REUSE). 많이 찾는 도시일수록 다음 요청이 빨라지고 Gemini를 덜 부른다.
- 무엇을 얼마나 보관할 수 있나:

| 데이터 | 보관 | 이유 |
| --- | --- | --- |
| 우리 분석 결과(관찰·해석·매칭, S3 JSON) | **계속** | 우리가 만든 데이터. 영상당 수십 KB라 Glacier 같은 보관 등급은 필요 없다(1만 개여도 수백 MB) |
| placeId | 계속 | Google 약관상 저장 허용 |
| 좌표 | 30일 이내(지금 25일) | Google 약관 |
| YouTube 영상 정보(제목·설명·채널) | **30일마다 새로 받아 갱신** | YouTube 개발자 정책: 30일 안에 갱신하거나 지운다. `videos.list`는 50개당 1 unit이라 계속 갱신해도 거의 공짜. 갱신 실패·비공개 전환이면 지운다 |
| YouTube 검색 결과 | 25일 뒤 만료(지금대로) | 검색은 100 units라 비싸고, 오래된 검색 결과는 쓸모가 줄어든다 |

- 즉 "YouTube 캐시를 안 지운다"는 **지우는 대신 갱신**으로 맞춘다. `cleanup`([매일])이 만료 임박한 영상 정보를 `videos.list`로 다시 받는다(TODO: cleanup 구현 때).
- 영상 수를 2개로 줄이지 않는다. 여러 채널 확인이 이 서비스의 핵심이고, 동시 실행이라 영상 수를 늘려도 시간은 거의 같다.

### 4. 목적지와 무관한 영상 거르기 ([1] `rules/selection.py`)

- 제목 또는 설명란에 목적지 표기가 있어야 후보로 남긴다. 표기는 한국어·원어·영어 별칭 목록(예: 오사카 / 大阪 / osaka, 설정값)으로 비교하고 NFKC·소문자로 맞춘다.
- 10/25 예: O4 "여행 후 다이어트 일상 복귀… ep26"(오사카 없음)은 빠진다. 정보 영상 판별은 하지 않는다.
- 기존 규칙(공개, 3분 이상, 최근 2년, 채널당 1개)은 그대로.

### 5. 503·느린 영상 대책 (결정 0006-5 보완)

- 영상마다 **마감 50초.** 넘기면 그 영상은 이번 결과에서 빼고 작업을 끝낸다. 늦은 영상은 혼자 끝까지 분석돼 다음 요청부터 재사용된다(영상 흐름을 작업과 따로 실행).
- 503·429면 재시도 대신 **다른 모델로 1회**(배정된 다른 모델 중 여유 있는 쪽). 그래도 실패하면 그 영상만 실패.
- 예비 영상 대체([3])는 1분 목표와 맞지 않아 **처음부터 예비 영상 1~2개를 같이 돌리고**, 먼저 끝난 5개로 결과를 만든다(예비는 두 모델 중 여유 있는 쪽에 배정). [3] 단계는 없앤다. 결정 0002-5를 고친다.
- 작업 전체 마감 80초. 그때까지 끝난 영상으로 결과(성공 영상이 5개 미만이면 PARTIAL).

- 생각 수준이 속도를 좌우한다. `minimal`은 **장소 이름은 다 잡고 평가 문장은 버린다.** `low`는 둘 사이.
- 토큰은 생각 수준과 상관없이 입력 약 2.8만(5분)·10.8만(전체)으로 같다. `low`·`minimal`은 생각 토큰이 0이라 출력 비용도 준다.
- Bedrock 해석·Places 매칭 시간은 아직 재지 않았다(게이트웨이 연결 전). 수 초~15초로 가정.

## 대안 (채택하지 않음)

- **앞 5분만 분석(T6, 24초):** 빠르지만 그 뒤 장소를 버린다. 요청을 쓰고도 결과가 반쪽이라 채택하지 않음(2026-10-25 팀 의견).
- **도시별 미리 분석(Scheduler):** 가장 빠르지만 도시 수만큼 Gemini 한도가 든다. 시연 도시 하나를 미리 채워 두는 용도로만 쓸 수 있다(필요하면 따로 결정).
- **영상 2개만 분석:** 빨라지지 않는다(동시 실행이라 시간은 가장 느린 영상 기준). 여러 채널 확인이 약해진다.
- **생각 `minimal` + 전체 영상(T7, 43초):** 장소는 영상 끝까지 잡지만 평가 문장이 거의 없어 평가·시간대 근거가 빈다. 장소 핀만 필요해지면 다시 본다.
- **기본 생각 + 전체 영상(지금):** 영상당 1~3분, 목표 불가.
- **S3 Glacier 보관:** 분석 결과가 작아 비용 차이가 없고, 재사용할 때 꺼내는 데 몇 분~몇 시간 걸려 오히려 느려진다.
- **관찰 출력을 스트리밍으로 받아 조각마다 해석:** [2-3] 해석이 단서 전체를 보고 묶는 구조와 맞지 않고 복잡하다.
