# 0009. 프론트 서버를 EC2로 (2026-11-05)

상태: **철회** (2026-11-05, 같은 날 사람 결정). 만들기 전에 기존 서버리스 구성(S3 + CloudFront)으로 되돌렸다. EC2 스크립트는 저장소에서 지웠고 커밋 `6e4a4d5`에 남아 있다. 아래는 당시 검토 내용이다.

## 배경

중간 발표(10/26)에서 "EC2로 가는 쪽인데 CloudFront·S3는 왜 있느냐"는 지적을 받았다. 팀이 EC2를 켜는 쪽으로 정했다.

## 결정

- 프론트 정적 파일과 `/api` 전달을 **EC2 한 대의 nginx**가 맡는다. CloudFront와 웹 버킷 `sgu-clicktotrip-web`은 만들지 않는다.
- 분석 파이프라인과 API는 그대로 Lambda·Step Functions·API Gateway다. EC2에 분석 로직을 두지 않는다.
- EC2에는 IAM 역할과 서버 키를 두지 않는다. 파일을 내려주고 요청을 넘기기만 한다.
- 브라우저는 EC2 하나만 보므로(같은 출처) CORS가 필요 없다.

## 바뀌는 것

| 항목 | 전 | 후 |
| --- | --- | --- |
| 화면 파일 | S3 + CloudFront | EC2 nginx (`infra/ec2/`) |
| `/api` 전달 | CloudFront 동작 | nginx `/api/` → API Gateway |
| 배포 | S3 업로드 | `infra/ec2/deploy_frontend.sh` (scp 대신 ssh로 전송) |
| CLAUDE.md "EC2 상시 서버 금지" | 금지 | 프론트 서버 1대만 허용 |

## 위험과 대응

| 위험 | 내용 | 대응 |
| --- | --- | --- |
| 허용 목록 | 결정 0007의 계정 회신 허용 목록에 EC2가 없다 | 콘솔에서 먼저 만들어 본다. 거부되면 담당자에게 묻는다 |
| HTTP | 인증서와 도메인이 없어 HTTP다. `guestAccessToken`이 평문으로 오간다. Google 로그인(M8)은 HTTPS가 필요하다 | 1단계 시연은 HTTP로 간다. M8 전에 EC2 앞에 CloudFront를 두거나 도메인을 붙인다(별도 결정) |
| 비용 | 쓰지 않아도 켜 둔 시간만큼 과금된다 | 시연·작업 때만 켠다 |
| IP 변경 | 중지 후 다시 켜면 공인 IP가 바뀌어 지도 키의 리퍼러 제한을 고쳐야 한다 | 고정이 필요해지면 Elastic IP |
| 운영 | OS 패치와 장애 대응을 직접 한다 | 서버 한 대, 상태 없음. 지우고 다시 만들 수 있게 스크립트로 둔다 |

## 대안 (채택하지 않음)

- **S3 + CloudFront 유지:** 운영 부담이 가장 적고 HTTPS가 기본이지만 팀이 EC2로 정했다. 위 위험이 커지면 되돌릴 수 있다. 프론트는 `VITE_API_BASE`만 쓰므로 코드는 바뀌지 않는다.
- **분석까지 EC2로 이전:** Step Functions·Lambda 코드를 다시 짜야 하고 이번 결정의 범위가 아니다.

## 확인할 것

1. 학교 계정에서 EC2 인스턴스, 키 페어, 보안 그룹을 만들 수 있는지.
2. 인스턴스 유형 제한과 비용 한도.
3. 이름 접두사 규칙: `sgu-clicktotrip-web`으로 만든다.
