# 0010. 유튜브 구독·좋아요로 취향 분석 (2026-11-19)

상태: **제안** (사람 확인 필요. 아래 "사람이 정할 것" 1~5)

2026-11-19 개정: 발표 지적 3("결국 비용이 늘어나는 구조")을 먼저 지키기로 해서, **취향 기능이 분석 비용을 늘리지 않는 것**을 원칙으로 넣고 2번(영상 선택)과 3번(저장)을 바꿨다.

근거: 중간 발표(10/26)에서 "일반 Claude·GPT에 묻는 것과 무엇이 다르냐"는 지적에 "유튜브 구독·좋아요로 개인 취향을 반영한다"고 답했고 반응이 좋았다. 명세에는 경로(spec §3.3)와 저장 형식(spec §4.4, `UserItem.youtube`)만 있고, **무엇을 어떻게 분석해 어디에 쓰는지**는 정해지지 않았다.

## 지금 있는 것과 없는 것

| 있음 | 없음 |
| --- | --- |
| `UserItem.youtube`(여행 채널, 좋아요한 여행 영상, 스타일 후보 점수), `preferences.referenceChannelIds` | `api_me` 핸들러(빈 껍데기) |
| 순위의 참고 채널 가중치(`rules/ranking.py` `REFERENCE_WEIGHT`) | 구독·좋아요 조회(`clients/youtube.py`) |
| 제목 키워드 스타일 규칙(`rules/style_tags.py`) | 여행 채널 판별·취향 분석 규칙 |
| 경로 명세: `POST /me/youtube/import`, `/confirm`, `DELETE /me/youtube/connection` | Google 로그인(M8), 연결·확인 화면 |

## 흐름 (기본안)

1. 로그인한 사용자가 "유튜브 연결"을 누른다. 브라우저가 Google에서 **짧은 수명의 액세스 토큰**(`youtube.readonly`)을 받는다.
2. 브라우저가 이 토큰을 헤더에 실어 `POST /me/youtube/import`를 **한 번** 부른다. 서버는 구독 채널과 좋아요한 영상을 읽고 토큰을 버린다(저장·로그 금지, 확정 결정 3).
3. 서버가 **후보**를 돌려준다: 여행 채널 후보, 스타일 비율 후보(맛집 60%, 카페 25% …).
4. 사용자가 화면에서 채널을 고르고 스타일을 고친 뒤 `POST /me/youtube/confirm`. **확인한 것만** 저장한다.
5. 이후 요청에서 저장된 취향을 쓴다(2번 결정).
6. `DELETE /me/youtube/connection` 또는 25일이 지나면 유튜브에서 온 데이터를 지운다.

## 비용 원칙 (발표 지적 3을 먼저 지킨다)

취향 기능은 **Gemini 관찰·Bedrock 해석 비용을 늘리지 않는다.** 아래 다섯 가지로 지킨다.

| # | 원칙 | 효과 |
| --- | --- | --- |
| 1 | 요청당 영상 수는 그대로 5개 | 요청 하나의 분석량이 늘지 않는다 |
| 2 | 개인 채널 영상은 **이미 분석된 영상**(`VideoAnalysis` DONE, 같은 분석 버전)**만** 섞는다 | 개인 영상 때문에 새로 Gemini를 부르는 일이 없다 |
| 3 | 채널 라벨(여행 채널인지, 스타일)은 **채널 단위로 25일 캐시**한다 | 같은 채널을 구독한 사람이 많아도 Bedrock은 채널당 한 번 |
| 4 | Bedrock에는 규칙으로 거른 여행 후보만 보낸다 | 입력 토큰 최소화 |
| 5 | YouTube는 1 unit 호출만 쓴다(`search.list` 100 unit 금지) | 검색 한도를 쓰지 않는다 |

남는 비용은 연결할 때의 YouTube 몇 unit과, 캐시에 없는 채널의 Bedrock 라벨 호출뿐이다.

## 결정 (기본안)

### 1. 분석 방법: 규칙으로 거르고, Bedrock이 라벨을 제안하고, 사람이 확정

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 1차 거르기 | 규칙 | 채널 이름·설명, 좋아요 영상 제목에 여행 키워드(여행, 브이로그, 해외, 도시 별칭 `DESTINATION_ALIASES` 등)가 있는 것만 후보로 |
| 라벨 제안 | Bedrock | 후보 채널마다 "여행 채널인가", 주로 다루는 스타일(5종)을 라벨로 제안. 근거 문장(입력 제목 원문) 필수 |
| 스타일 비율 | 규칙 | 좋아요한 여행 영상 제목에 `style_tags.video_styles`를 적용해 비율 계산 |
| 확정 | **사용자** | 화면에서 고르고 고친 것만 저장 |

- "AI는 결론을 내리지 않는다"(CLAUDE.md)와 맞다. Bedrock은 후보 라벨만 내고, 저장은 사람이 확인한 것만 한다.
- Bedrock에 넘기는 것은 **공개 채널·영상의 제목과 설명뿐**이다. 사용자 ID, 이메일, 토큰은 넘기지 않는다.
- 규칙만으로 하는 안(대안 A)과 결과를 비교할 수 있게 둘 다 테스트 fixture로 남긴다(M7 비교와 같은 방식).

### 2. 취향이 쓰이는 곳: 순위 + 캐시된 개인 영상

| 범위 | 내용 | 추가 분석 비용 |
| --- | --- | --- |
| **순위** | 확인한 참고 채널이 방문한 장소에 가중치(이미 구현), 스타일 비율을 요청 스타일 기본값으로 | 없음 |
| **영상 선택** | collect가 영상 5개 중 **최대 2개**를 사용자가 확인한 여행 채널의 해당 도시 영상으로 채운다. 단, **이미 분석된 영상만** 넣는다. 없으면 지금처럼 일반 검색 5개 | 없음(캐시 재사용) |

- 찾는 방법: 확인한 채널의 업로드 목록(`playlistItems.list`, 1 unit)에서 제목·설명에 목적지 표기(`DESTINATION_ALIASES`)가 있는 영상을 고르고, `VideoAnalysis`에 DONE이 있는지 확인한다(DynamoDB 조회만).
- 이렇게 하면 개인 영상이 섞여도 Gemini를 새로 부르지 않는다. 대신 **처음에는 효과가 작다.** 캐시가 쌓일수록(많이 찾는 도시일수록) 개인 영상이 더 자주 들어간다.
- 개인 채널의 도시 영상이 캐시에 없을 때 그 영상을 미리 분석해 둘지(예: 하루 상한 안에서 밤에)는 이번 범위가 아니다. 필요하면 따로 결정한다.

### 3. 저장: 사용자가 확인한 것과 API에서 온 것을 나눈다 (spec §4.4 유지)

| 속성 | 내용 | 보관 |
| --- | --- | --- |
| `preferences.referenceChannelIds`, `preferences.styles` | 사용자가 확인한 참고 채널·스타일 | 사용자가 지울 때까지 |
| `youtube.travelChannelIds`, `youtube.styleProfileCandidate` | API에서 온 원본 후보 | 25일(`resyncDueAt`), 연결 해제 시 즉시 삭제 |
| `youtube.likedTravelVideoIds` | **저장하지 않는다**(빈 목록 유지) | - |
| YoutubeCache `CHANNEL#{channelId}` / `TASTE` | 채널 라벨 캐시(여행 채널 여부, 스타일, 근거 문장, 분석 버전). 사용자와 무관한 공개 채널 정보 | 25일(기존 YoutubeCache TTL과 같음) |

- 좋아요한 영상 ID 목록은 분석이 끝나면 필요 없다. 최소한만 저장한다.
- 채널 이름·영상 제목은 저장하지 않는다(ID만). 화면에 보일 때는 조회 응답으로만 준다.
- 채널 라벨 캐시는 누가 구독했는지 담지 않는다. 사용자별 정보는 Users에만 있다.

### 5. 로그인·Google 설정 (M8 선행)

- 로그인은 결정 0007-2대로 Google ID 토큰 + API Gateway JWT Authorizer. `/me/*`는 로그인 경로에만 둔다.
- 유튜브 권한은 로그인 때 받지 않고 **연결 버튼을 누를 때만** 따로 요청한다(점진적 승인).
- OAuth 동의 화면은 **테스트 모드**로 두고 팀원·시연 계정만 테스트 사용자로 등록한다. TODO(verify): `youtube.readonly`가 Google 심사 대상 범위인지, 테스트 모드에서 심사 없이 쓸 수 있는지.

## 대안 (채택하지 않음)

- **A. 규칙만:** 비용·지연·외부 전송이 없다. 채널 설명이 짧거나 영어면 놓친다. Bedrock 활용 필수 조건과 발표 흐름에도 약하다. 1번의 비교 대상으로 남긴다.
- **B. Bedrock만(규칙 거르기 없이 전체 구독 전송):** 구독이 많으면 입력이 커지고, 여행과 무관한 개인 구독까지 외부로 보낸다.
- **C. 순위만 반영:** 가장 단순하다. 결과 지도가 거의 같아 차별점이 약하다. 기본안도 캐시가 쌓이기 전에는 사실상 이것과 같다.
- **F. 개인 영상을 캐시와 무관하게 2개까지 새로 분석:** 차별점은 가장 크지만, 사람마다 영상이 달라져 캐시 재사용이 줄고 첫 분석 비용이 늘어난다. 지적 3과 충돌해 채택하지 않는다.
- **D. refresh 토큰 저장 후 주기 동기화:** 확정 결정 3(토큰 미저장) 위반.
- **E. 좋아요 수·구독자 수로 가중치:** CLAUDE.md 금지(인기 지표는 점수에 쓰지 않는다).

## 사람이 정할 것

1. 분석 방법: 기본안(규칙 → Bedrock 제안 → 사용자 확인)으로 갈지, 규칙만(대안 A)으로 갈지.
2. 쓰이는 곳: 순위 + **캐시된** 개인 영상 최대 2개(기본안)인지, 순위만(대안 C)인지. 2개라는 숫자도. 캐시에 없는 개인 영상을 새로 분석하는 대안 F는 비용 때문에 뺐다.
3. 사용자 구독 채널의 공개 제목·설명을 학교 LLM 게이트웨이로 보내도 되는지. 게이트웨이는 요청을 일정 기간 로그에 남긴다(결정 0007-1). 사용자 식별 정보는 보내지 않지만, 화면에 "분석을 위해 외부 AI에 채널 제목을 보낸다"는 안내를 넣을지.
4. Google OAuth 동의 화면 설정(테스트 사용자 명단)을 누가 언제 할지.
5. 순서: M5 배포 → M8 로그인 → 이 기능, 아니면 로그인 없이 백엔드 규칙·핸들러부터 먼저 구현(테스트는 가짜 데이터로)할지.
