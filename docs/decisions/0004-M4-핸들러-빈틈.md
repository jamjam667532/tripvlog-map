## 1. `claim`을 별도 Lambda로 둔다 (AGENTS.md §7 열린 질문)

- 문제: spec M4에는 `claim` 핸들러가 있지만 CLAUDE.md의 핸들러 목록에는 없다.
- 기본안: `backend/functions/claim/` Lambda를 둔다. 선점 규칙(없음/DONE/ANALYZING+기한/FAILED)이 조건부 쓰기 + 재조회 + Jobs 갱신까지 이어져서, Step Functions의 DynamoDB 직접 연동으로는 분기와 테스트가 어렵다.
- 대안: Step Functions `dynamodb:putItem` 직접 연동 + Choice 상태. Lambda 호출 비용은 줄지만 규칙이 ASL에 흩어진다.
- 영향: CLAUDE.md 핸들러 목록, CI 이미지 매트릭스, M5 CDK.

## 2. 실패 기록과 대체 영상 연결을 어느 Lambda가 하는가

- 문제: Map 항목이 실패(Catch)했을 때 Jobs·VideoAnalysis를 FAILED로 바꾸는 단계, 그리고 결정 0002-5의 예비 영상 대체를 실행하는 단계가 명세에 없다.
- 기본안:
  - 실패 기록은 `claim` Lambda의 `action: "fail"`. 선점 주체가 이 작업일 때만 VideoAnalysis를 FAILED로 바꾼다. 오류는 Step Functions `Error` 이름만 저장하고 `Cause`(원문이 섞일 수 있음)는 버린다.
  - 대체 선택은 `aggregate` Lambda의 `action: "replace"`. 대체 영상이 있으면 같은 영상 흐름(claim→observe→interpret→match)을 다시 돌리고 다시 `replace`로 돌아온다. 상한(`MAX_REPLACEMENTS_PER_JOB`)에 닿거나 고를 영상이 없으면 `action: "aggregate"`.
  - 대체로 뽑힌 예비 영상은 `spareVideos`에서 빼고 `videoRefs`에 `replaces`와 함께 넣는다(채널 중복 검증 때문).
- 흐름 전체는 `backend/shared/schemas/events.py` 문서 문자열과 `backend/tests/integration/pipeline.py`(Step Functions 흉내)에 있다.

## 3. 미확정 후보와 영상 기반 표기를 어디에 두는가

- 문제: 결과 JSON의 `unconfirmed`(이름 목록)와 `name`("이치란 · 도톤보리" = 영상 이름 + `branch_hint`)을 aggregate가 만들어야 하는데, Places 테이블의 PLACE 아이템에는 `branch_hint`가 없고 미확정 후보를 둘 곳도 없다. 분석을 재사용하는 작업은 match를 다시 돌리지 않으므로 영상 단위로 남아 있어야 한다.
- 기본안: match가 영상별 매칭 요약을 S3 `analysis/{videoId}/{version}/match.json`에 쓴다(`schemas/match.py` `MatchSummary`): 확정 장소의 placeId·영상 기반 표기·분류, 미확정 후보의 이름·placeId 목록, 버린 후보 수. Google 응답의 이름·주소는 넣지 않는다. 미확정 근거는 Places 테이블에 쓰지 않는다(`matchStatus`는 CONFIRMED만 저장).
- 같은 장소를 여러 영상이 확정하면 표기는 가장 많이 나온 것, 같으면 채널 ID 순 첫 번째.

## 4. 재사용한 분석의 좌표가 만료된 경우

- 문제: 분석(VideoAnalysis DONE)은 버전이 같으면 계속 재사용하지만 좌표(CoordCache)는 25일이 지나면 쓸 수 없다. 재사용 시 match를 다시 돌리지 않으므로 좌표가 없는 장소가 생긴다.
- 기본안(임시): aggregate는 좌표가 없는 장소를 지도 결과에서 뺀다. 순위는 남은 장소로 다시 매긴다.
- 제안: M5 이후 Places Place Details(`id`, `location` 필드만)로 좌표만 다시 받는 `PlacesClient.locate_place(place_id)`를 추가한다(클라이언트 인터페이스 변경이라 별도 PR).

## 5. YouTube 일일 검색 횟수 카운터

- 문제: spec §5.1 "일일 검색 횟수 카운터를 두고 상한 초과 시 캐시만 사용"의 저장 위치가 없다.
- 기본안: YoutubeCache 테이블에 `pk = QUOTA#{YYYY-MM-DD}(UTC)`, `sk = SEARCH`, `count`, `expiresAt(+2일)` 아이템(`YoutubeQuotaItem`, 스키마 추가만). 원자적 ADD + 조건 `count < 상한`. 상한 기본 90회(= 9,000 units), `DAILY_SEARCH_LIMIT` 환경 변수. TODO(verify): 실제 할당량.

## 6. requestId 중복 처리를 원자적으로

- 문제: spec §3.1은 같은 requestId면 기존 jobId를 409로 돌려주라고 하는데, `requestId-index` GSI는 최종 일관성이라 동시에 두 요청이 오면 작업이 둘 생길 수 있다.
- 기본안: `jobId`를 `requestId`에서 결정적으로 만든다(sha256 앞 16바이트에 UUID v4 비트를 씌움). 같은 requestId는 같은 jobId → `attribute_not_exists(jobId)` 조건부 쓰기로 원자적으로 막힌다. 조회에는 여전히 guestAccessToken이 필요하므로 jobId를 알아도 결과를 볼 수 없다. GSI는 그대로 둔다(M8 `/jobs`에서 사용 가능).

## 7. 작은 선택 (이의 있으면 알려 주세요)

- 검색 정렬 혼합: `"{dest} 브이로그"`·`"{dest} 맛집"`은 relevance, `"{dest} 여행"`은 date. 결과는 세 목록을 번갈아 합친다. 1페이지 25개.
- 검색 캐시 해시의 기간 필터는 "2년 전 달의 1일"로 맞춘다(매일 해시가 바뀌어 캐시가 무의미해지는 것을 막음). 정확한 "최근 2년" 필터는 메타데이터 규칙에서 다시 건다.
- 스타일 키워드 태깅(Nova 미사용 시): 제목+설명란에 스타일별 키워드가 있으면 그 스타일, 둘 이상이면 `복합`, 없으면 `분류불가`. 선호 스타일과 겹치는 영상을 앞으로 당기되 채널당 1개가 먼저다.
- `search_queries`가 비어 있으면 후보의 `names` 앞 2개로 검색한다(영상에 나온 표기이므로 "근거 없는 상호 생성"이 아님).
- 근거 아이템의 재생 구간은 `clue_refs` 단서들의 최소 start ~ 최대 end, 근거 문장은 utterance → seen_text → heard_name → scene 순으로 첫 값.
- 지역 묶음(`areaGroup`)은 약 2 km 격자. 이름은 Google 응답을 쓸 수 없어 `지역 1`, `지역 2`…(가장 높은 순위 장소가 있는 묶음부터). M6 화면에서 바꿀 수 있다.
- 공개 경로 요청 제한(IP·전역 일일 예산, 429)은 API Gateway·WAF 설정과 함께 M5에서 한다.
- 진행률 `progress.total`은 대체 영상을 포함한 `videoRefs` 수, `analyzed`는 DONE, `failed`는 FAILED 수.
- 도시 위치 편향 좌표는 match가 영상마다 `places.locate(destination)`로 받는다(작업당 최대 5~6회). 비용이 문제되면 M7에서 캐시한다.
